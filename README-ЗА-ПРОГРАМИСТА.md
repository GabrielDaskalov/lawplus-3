# Law+ — техническо резюме

Този пакет отговаря на оценката, че фронтендът „в този си вид е на практика
карта капан“.

**Дизайнът и функциите на сайта са запазени изцяло.** Нищо не е
преработвано „на ново“: същите екрани, същият вид, същите възможности —
включително помодоро таймера, изпитния жребий, SRS преговора, тетрадката на
грешките, латинския речник, AI асистента и админската конзола.

Променено е това, което правеше сайта неподдържаем и неплатим:
**структурата, източникът на данните и проверката на достъпа.**

Всичко тук е компилирано, стартирано и проверено срещу истински PostgreSQL,
истински backend и истински браузър — не е само написано.

---

## 1. Какво точно беше счупено

### 1.1. Плащането не пазеше нищо

Учебното съдържание живееше в `pravo-academy-data.js` — **12,5 MB**, които се
сваляха от всеки посетител преди вход и преди плащане. Заключването беше в
браузъра, върху данни, които вече бяха у посетителя. `view-source` ги показва.

Същата дупка беше и в backend-а: `GET /api/content` беше **публичен** маршрут,
който връщаше пълния blob с всички дисциплини. Един адрес, без вход.

> Това е причината за „карта капан“. Не е фронтенд проблем, а продуктов:
> продуктът се раздаваше безплатно на всеки, който погледне.

### 1.2. Съдържанието живееше в кода

Въпроси, конспекти и казуси бяха записани вътре в JavaScript файла. Поправка
на една запетайка изискваше програмист и ново качване на 13 MB. Админският
панел „редактираше“ в localStorage — тоест промяната се виждаше само от
компютъра на админа, а студентите продължаваха да учат старото.

### 1.3. Отговорите пътуваха заедно с въпросите

Верният отговор беше в същия обект, който се подаваше на екрана.

### 1.4. Нямаше система за сглобяване

Един файл от 13 MB, без компилация, без модули, без тестове.

## 2. Какво е направено

### 2.1. Съдържанието е извадено в нормализирана база

`content/scripts/extract.mjs` чете стария монолит и произвежда проверени JSON
файлове; внасят се с `backend-patch/scripts/import-content.ts` (идемпотентен,
транзакционен, с `--dry-run`).

Реално внесено и преброено:

| | брой |
|---|---|
| предмети | 11 |
| теми | 509 |
| конспекти | 498 |
| флашкарти | 2 627 |
| тестови въпроси | 4 579 |
| — с избор (`mcq`) | 3 597 |
| — със свободен отговор (`fill`) | 982 |
| казуси | 690 |

Схемата е `backend-patch/migrations/010_content_model.sql`.

**Две неща, които извличането хвана и които биха се загубили тихо:**

* **982 упражнения по латински** се нормализираха като въпроси с избор без
  опции — тоест ставаха неотговорими. Затова има колона `kind`
  (`'mcq' | 'fill'`) с отделни CHECK ограничения. Хвана се чак при истинския
  внос, не при четене на кода.
* **134 флашкарти** нямаха връзка към тема. Възстановени по заглавие;
  проверено — 0 останали.

### 2.2. Фронтендът: същият сайт, вече проект

Един файл от 13 MB → **58 модула + CSS + `index.html`**, сглобени с Vite.

Разделянето е механично, с инструмент, не на ръка: секциите на стария
`app.js` стават модули; `export`/`import` се генерират чрез разбор на кода
(`acorn`), а не с търсене по текст; `main.js` ги внася **в стария ред**,
защото част от тях се изпълняват при зареждане.

| | преди | сега |
|---|---|---|
| първо зареждане | **13 MB** | **469 KB** (95 KB компресиран JS) |
| учебно съдържание в бъндъла | 12,5 MB | **0** |
| админски панел и правни текстове | винаги | теглят се при отваряне |

Подробности — `site/README.md`.

### 2.3. Достъпът се проверява на сървъра

`backend-patch/routes/content.ts`. Едно място решава „има ли право този
потребител“ — `assertTopicAccess`, стъпило на SQL функцията
`user_has_subject(uuid, varchar)`.

**Верните отговори не се селектират заедно с въпросите.** Проверката е
отделна заявка (`POST /content/quiz/:id/check`). Примерното решение на казус
също се тегли отделно, при натискане на бутона.

### 2.4. Админският панел редактира базата

`backend-patch/routes/adminContent.ts` + `site/src/lib/admin-content.js`.
Формите в панела не са пипани — добавен е само преводът между вида на данните
в екрана и вида в API-то.

* Валидация **преди** базата, с грешки по полета (CHECK ограниченията са
  последна преграда, не първа — съобщенията им са на латиница).
* Смяната на опции изисква нов верен отговор — иначе старият индекс сочи вече
  друг текст и въпросът тихо става грешен.
* Обясненията по грешна опция се пазят **по индекс**, не по буква (приемат се
  и букви при внос и се превръщат) — иначе при разбъркване на опциите
  обяснението почва да обяснява друг отговор.
* Всяка промяна оставя следа в `content_revisions` със старата стойност.
* Масовият внос е „всичко или нищо“, с ясен списък какво не е наред.

**Проверено на живо:** редакция от панела → `PATCH 200` → стойността е в
базата → журналът записва кой, кога и какво е било преди.

### 2.5. Поправки в съществуващия backend

| файл | какво |
|---|---|
| `routes/account.ts` | `GET /api/content` вече иска админ. Беше публичен и връщаше цялото платено съдържание. |
| `middleware/errorHandler.ts` | пренася грешките по полета; не пише 4xx в дневника |
| `routes/content.new.ts` | търсенето връщаше суров JSON и не проверяваше достъпа; админът вижда всичко |
| `index.ts` | **изключени стари маршрути**, които четяха платено съдържание без вход (`/api/flashcards`, `/api/cases`, `/api/conspects`, `/api/lectures`, `/api/quiz`, `/api/search`) |
| `index.ts` + `config.ts` | ограничаването на заявките е по потребител, не по IP (виж по-долу) |
| `middleware/optionalAuth.ts` | нов; при срив на базата пада към **по-малко** права |

Подробностите са в `backend-patch/patches/`.

**Отделно: `ОДИТ-НА-BACKEND.md`** казва какво в backend-а е проверено, какво
е поправено и — важното — **какво НЕ е проверявано** (плащанията са в този
списък).

## 3. Какво намериха проверките

Това не са теоретични подобрения. Всяко от тези е било реален дефект, хванат
при пускане:

1. **Всеки отказ щеше да излиза като „500 сървърна грешка“.** Новите маршрути
   хвърляха собствен клас грешка, който централният `errorHandler` не
   разпознава. Тоест paywall-ът работеше, но се оплакваше грешно.
2. **Обясненията по сгрешена опция никога нямаше да се покажат.** Екранът ги
   търсеше по буква (А/Б/В/Г), а се пазят по индекс.
3. **След вход платеното оставаше празно.** Кешът пазеше отказите отпреди
   входа и не се пресичаше при смяна на правата.
4. **Конспектът зареждаше една тема, а показваше друга.** Екранът чете
   `?chapter=`, а зареждането ползваше `?t=`.
5. **`429 Too Many Requests` при нормална употреба.** 100 заявки / 15 мин по
   **IP адрес** — една университетска мрежа изчерпва квотата за всички.
6. **Тестът по по-задна тема излизаше празен.** Зареждаха се първите 100 от
   750 въпроса; сега избраните теми се теглят поименно.
7. **Търсенето показваше суров JSON** и връщаше откъси от некупени дисциплини.
8. **Без сървър цялата витрина се чупеше** — вместо да покаже рекламните
   страници от кода.
9. **Paywall-ът се заобикаляше с друг адрес.** Освен новите `/api/content/*`
   бяха монтирани и стари маршрути за същото съдържание, без никаква
   проверка. Проверено на живо: `GET /api/flashcards` връщаше платени карти
   на анонимен посетител, а `POST /api/conspects` пишеше без вход.

## 5. Как се пуска

Пакетът е **пълен** — backend, фронтенд и съдържание. Поправките вече са
приложени в `backend/`; няма какво да се слива на ръка.

Стъпките са в **`КАК-СЕ-ПУСКА.md`**. Накратко:

```bash
psql lawplus -f backend/src/db/schema.sql
psql lawplus -f backend/migrations/010_content_model.sql
cd backend && cp .env.example .env && npm install && npm run dev
npx ts-node scripts/import-content.ts --dry-run && npx ts-node scripts/import-content.ts
cd ../site && npm install && npm run build
```

Какво точно е пипано в backend-а и защо — в `промени/`.

**Задължително преди пускане на живо:** смени `JWT_SECRET`. По подразбиране е
`change-me-in-production`.

## 6. Какво остава

Честно, за да не се търси:

1. **Модулите носят стария стил** — глобални функции, шаблонни низове,
   `innerHTML`. Разделянето нарочно не пипна съдържанието на функциите; целта
   беше нулева промяна в поведението. Почистването е следваща стъпка, вече по
   един файл.
2. **Няма типове** във фронтенда. `jsconfig.json` + `// @ts-check` по файлове
   е евтиното начало.
3. **`onclick` в шаблоните** работят през мост към `window` (26 функции,
   изброени в `main.js`). Минаването към `addEventListener` е механично.
4. **`middleware/auth.ts` пада „отворено“** при срив на базата — свален админ
   може да мине. Новият `optionalAuth.ts` пада в обратната посока. Оставено
   непроменено нарочно: чужд код в пътя на всяка заявка. **Препоръка:** да се
   изравни.
5. **Плащанията не са пипани.** Stripe маршрутите са както са били.
6. **AI асистентът** вижда само свалените материали. За работа върху целия
   предмет иска собствен маршрут на сървъра.
7. **Партидите с въпроси (теми 1–47)** са готови за
   `POST /admin/content/subjects/:code/import`, но още не са внесени.
   **Теми 17 и 24 липсват** от подадения материал.
8. **Няма CI.** Проверките се пускат на ръка.

## 7. Какво значи това за оценката 250–300 часа

Оценката предполага започване от нулата. Тук вече са налице: схемата,
извличането на съдържанието с решените проблеми, проверката на достъпа на
сървъра, админското API, фронтендът със сглобяване и модули — при запазен
дизайн и запазени функции — и проверките към всичко изброено.

Остатъкът е списъкът в точка 6: преглед, пускане в експлоатация и внос на
подготвените партиди.
